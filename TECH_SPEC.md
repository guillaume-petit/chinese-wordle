**Design principles:**

- **The game core is pure TypeScript.** No React, DOM, storage, or time access. It is fully unit-testable.
- **Side effects live in services.** Each service has an interface plus web and Android implementations where needed.
- **The suggestion engine is isolated from puzzle data.** It must not be able to see the answer (§4.3).
- **The clock is injected.** All date logic receives time from a `Clock` service so tests can control it.
- **The visual system is theme-token driven.** A warm ruled-paper canvas, ink-like text, and bamboo/forest-green accents should carry consistently across screens; dark appearance uses the same palette intent with accessible contrast. Render a dashed 米字格 guide as a tile background behind characters and feedback marks. Use a separate platform-native handwritten/calligraphic CJK font stack for guess-tile characters only, selecting `.tile-character` through the parent tile's `lang` attribute; don't bundle decorative fonts.
- Character tiles derive their `--tile-paper` background from the feedback state, mixing its color with the theme surface. Guess tiles use a responsive `--tile-size` (60/64/72px) with font size set to 90% of the square, targeting roughly 75-80% visible glyph coverage depending on font metrics. Each wrapper reserves 28px above its square for a centered tone marker with a transparent background. Tones 1-4 retain 24x12px inline SVG brush shapes filled with `currentColor` in a 30x15px marker; the neutral tone retains its 28px text glyph. Both sit entirely above the square and retain accessible tone labels. Feedback icons use smaller, lighter-weight text; compact result tiles retain their solid feedback colors.

## 4. Content and data

### Implemented bundled-dictionary milestone

The flat React app loads only currently approved curated learning records (`Word`) through `src/data.ts`. `src/dictionary.ts` exposes generated CC-CEDICT records and separate ID/form maps from `src/generated/dictionary.json`. `DictionaryEntry` holds canonical forms, written variants, all readings, English glosses, and nullable frequency. Suggestion labels show the best matching reading; selected readings persist with guesses. Dictionary entries alone cannot become answers. No MVP identifiers, learning records, pronunciation overrides, or compatibility archives remain.

`npm run content:build -- --source content\cedict-source.txt.gz` parses a manually downloaded snapshot and generates local JSON. Ordinary builds use generated data offline. The importer records provenance and SHA-256, filters unsupported characters/readings, normalizes pinyin, and merges canonical forms/readings. IDs derive from simplified code points; no starter overrides are injected. Malformed lines and invalid frequency overlays fail explicitly.

Unknown corpus ranks are `null`, not starter-list ranks. An optional `--frequency` JSON overlay must contain source attribution, license metadata, and positive integer ranks. Search sorts unknowns last, then by pinyin and simplified form. No answer eligibility, topic, hint, or schedule participates in ranking.

`src/pinyin.ts` imports dictionary data and types only, not curated learning records or answer selection. Tone-mark lookup, syllable membership, and prefix membership are precomputed once. A cached reading index buckets every pronunciation by the initial letter of its first syllable; each query is normalized and segmented once, scans only that bucket, and keeps the best match per dictionary ID. Typed tones remain constraints even for abbreviations. The first milestone remains in-thread with eager bundled JSON; lazy binary/gloss loading and a worker below are target architecture, not implemented features. Desktop full-snapshot query latency is checked against 100 ms; mid-range Android keystroke-to-render latency still requires device measurement, and a worker is required if it misses that target.

The generated dictionary is CC BY-SA 4.0. `THIRD_PARTY_NOTICES.md` and `public/licenses/` contain attribution, modifications, and license text. Workbox precaches license text along with the dictionary-bearing app bundle; the cache-size ceiling allows the full payload.

The bundled 2026-10-11 snapshot has tens of thousands of two-character entries. The full JSON is roughly 20 MB raw / 3.3 MB gzip. This eager payload is not the production <= 1.5 MB lazy search index described below; compact index/gloss payloads and mobile measurements remain release work.

The rest of this section and §5 describe the intended production content pipeline; binary output, separated gloss payloads, worker loading, and reviewed 90-day scheduling remain deferred.

### Planned TOCFL curation and weekday scheduling

Curated answer records will carry `tocflLevel: 1 | 2 | 3 | 4 | 5 | 6` and source-edition/entry provenance, separate from dictionary data and search ranking. This is vocabulary classification, not a computed or guaranteed puzzle-difficulty score. Verify source reuse terms and level mappings before importing; do not assign guessed levels to the starter records.

The future schedule builder selects reviewed eligible answers by the Asia/Shanghai calendar weekday: Monday-Saturday require TOCFL levels 1-6 respectively; Sunday selects a reviewed curated wildcard. Validate the scheduled answer's level against its date. A missing level pool blocks publication with an explicit content-validation error rather than silently substituting another level. The implemented heading displays the Chinese-formatted puzzle date and weekday vocabulary band: Monday-Tuesday Novice, Wednesday-Thursday Intermediate, and Friday-Saturday Advanced; omit the band on Sunday. The band is presentation metadata and does not affect autocomplete ordering.

The current import/curation target remains exactly two supported Han characters in both written forms and two aligned syllables. Exclude single-character TOCFL entries; defer three-/four-character entries from playable content, without truncating or splitting them. Variable-length puzzles would require changes to the dictionary importer, pinyin segmentation, guess validation, grid, feedback, and persisted content model, and need a separate scope decision.

Import every qualifying two-character TOCFL entry into a candidate collection before answer publication. Preserve source row/edition and level provenance when deduplicating explicit written forms; conflicting source levels or senses require review rather than silently choosing a level. Flag proper names, variant-only rows, ambiguous readings/senses, and script/form collisions. Polyphonic entries remain candidates when a reviewed intended reading can be selected. Match candidates to dictionary IDs using recognized explicit forms and verify aligned two-syllable readings; an unmatched entry requires a reviewed dictionary override or explicit exclusion, not an automatic conversion or silent drop. Candidate inclusion does not require authored hints/examples; publication as an answer does.

Weekday scheduling remains planned. `tools/import-tocfl.mjs` imports the supplied `content/tocfl-202307.csv` reference format (`ID,Traditional,Simplified,Pinyin,POS,Variants`), not arbitrary official spreadsheet formats. Source IDs `L0`-`L5` map to stored levels 1-6.

### Implemented spreadsheet curation

`content/curated-words.csv` is the editorial source of truth. `tools/build-curated.mjs` parses quoted UTF-8 CSV, including BOM, CRLF, embedded commas, escaped quotes, and multiline cells. Columns cover dictionary ID, both forms, `tocflLevel`, `sourceReference`, `reviewStatus`, `exclusionReason`, `pinyinNumbered`, optional tone alternatives/display spelling, and all learning fields. Candidate rows can omit learning content; only validated approved rows populate `answerIds`.

`npm run content:curated` generates `src/generated/curated.json` offline using the existing dictionary. It runs automatically before `npm run dev` and `npm run build`, and fails explicitly before overwriting output on validation errors. `src/data.ts` loads generated learning records and resolves approved IDs into `answerPool`. A TOCFL level, when supplied, appears in the game heading; Monday-Saturday level scheduling remains deferred until the source pool is complete.

The spreadsheet contains imported TOCFL candidates and excluded form pairs, with no MVP rows. `npm run content:tocfl` performs local explicit-form matching, expands supplied JSON variants, filters to two supported Han characters in both scripts, and produces `content/tocfl-import-report.json`. It deduplicates canonical dictionary IDs and retains every source ID/form/reading/level in report provenance. Conflicting source levels select the lowest (first introduction) explicitly, with all levels reported. Unmatched form pairs are excluded rather than dropped. Numbered/display pinyin comes from a dictionary reading; source-reading mismatches are reported for review.

The reference importer refuses to overwrite nonempty editorial content unless `--replace` is explicitly passed. Reimporting with replacement resets editorial changes; normal dev/build runs only curate the edited CSV, never reimport the reference. CSV parsing/serialization is shared with the curation tool. Source reuse terms still need verification; the importer does not assign a license to the user-supplied reference.

The curator does not read prior generated content or a compatibility archive: only currently approved CSV rows generate learning records. Every candidate/approved row requires level/source provenance; approved forms/readings must match its canonical dictionary ID.

CSV import tests run with the dictionary importer tests via `npm run test:importer`. Ordinary app builds need neither a downloaded CC-CEDICT source nor external spreadsheet tooling.

Empty or candidate-only input produces an empty artifact and explicit warning. `App` renders a no-approved-words screen before mounting puzzle hooks, so stale MVP saves cannot cause empty-pool selection. Storage excludes games/saved IDs whose answers were removed and guesses whose dictionary IDs no longer exist. General practice reports when no approved alternative to today's answer is available. Test-only synthetic vocabulary exercises gameplay without repopulating production content.

### 4.2 Data model

```ts
type WordId = string;          // Stable, e.g. "w_00421"
type Script = "simplified" | "traditional";
type Tone = 1 | 2 | 3 | 4 | 5; // 5 = neutral

interface Syllable {
  base: string;  // Normalized toneless form, "v" for ü: "peng", "lv"
  tone: Tone;
}

interface Reading {
  syllables: [Syllable, Syllable];
  display: string;              // Tone-marked: "péngyou"
}

/** Every accepted guess. Used by validation and suggestions. */
interface DictionaryEntry {
  id: WordId;
  simplified: string;           // Exactly 2 characters
  traditional: string;          // Exactly 2 characters
  variants: string[];           // Other accepted 2-character written forms
  readings: Reading[];          // All valid readings (多音 words have several)
  frequencyRank: number;        // 1 = most frequent
}

/** Curated answer content. Only for words in the answer pool. */
interface AnswerEntry {
  wordId: WordId;
  reading: Reading;             // The intended reading
  definition: string;
  example: { zhSimplified: string; zhTraditional: string; en: string };
  sentenceHint: { zhSimplified: string; zhTraditional: string; en: string }; // Answer blanked in both languages
  topic: string;
  difficulty: 1 | 2 | 3;
  audio: string | null;         // Path under /audio
}

interface ScheduleEntry {
  date: string;                 // "YYYY-MM-DD", Asia/Shanghai calendar date
  puzzleId: string;             // e.g. "d_2026-10-11"
  wordId: WordId;
}

interface ContentManifest {
  contentVersion: string;       // e.g. "2026.10.1"
  files: {
    answers: string;
    schedule: string;
    dictionary: string;
    glosses: string;
  };
  scheduleEnd: string;          // Last date covered by the schedule
}
```

**Gloss data is stored separately** (`glosses.<hash>.json`, keyed by `WordId`) so it can be loaded after the main index and skipped when glosses are turned off.

### 4.3 Answer isolation

The suggestion engine must not be able to leak the answer through ranking.

- `src/input/**` must not import from `src/core/dailyPuzzle.ts`, `src/services/content/answers*`, or anything that loads answers or the schedule. **Enforce this with an ESLint import-restriction rule.**
- The dictionary file contains **no answer-eligibility flag** and no difficulty data.
- The worker only receives the dictionary, the selected script, the typed input, and the list of already-submitted word IDs.
- An automated test verifies that ranked results are identical across different answers (§13).

**Answers are not secret.** The answer and schedule files are bundled for offline play, so a determined player can read them. To avoid accidental spoilers, store answer word IDs in the schedule (not characters), and don't log answers to the console. Competitive features are out of scope for this reason.

### 4.4 Content build pipeline

`npm run content:build` runs the tools in order:

1. **`build-dictionary.ts`**
   - Parses CC-CEDICT and keeps entries whose simplified and traditional forms are both exactly two characters.
   - Excludes entries that are proper nouns, surnames, or variant-only references.
   - Normalizes pinyin: lowercase, `u:` → `v`, tone numbers 1–5.
   - Merges entries with identical forms, collecting all readings.
   - Applies `content/overrides.yaml`.
   - Attaches frequency ranks; unknown words go to the end.
   - Writes the binary index (§5.4) and the glosses file.
2. **`build-schedule.ts`**
   - Reads `content/schedule.yaml` and resolves each date to a `WordId`.
3. **`validate-content.ts`** — fails the build if any check fails:
   - Every answer exists in the dictionary.
   - Every answer has two characters in both scripts, and its intended reading is one of the dictionary readings.
   - OpenCC conversion of the answer agrees with its curated forms, or the answer is listed as a reviewed exception.
   - Every answer has a definition, example, sentence hint, topic, and audio (or an explicit `audio: null`).
   - The sentence hint contains no answer characters in either script.
   - The schedule has no gaps and no duplicate dates, and no word repeats within 365 days.
   - The schedule covers at least **90 days** beyond the release date.
4. Writes content-hashed file names and `manifest.json`.

Generated files go in `public/data/` and are committed, so builds are reproducible without the source dictionary.

## 5. Pinyin input engine

### 5.1 Input normalization

Runs on every keystroke:

1. Trim; convert to lowercase; convert full-width Latin letters to half-width.
2. Convert tone-marked vowels to the base vowel plus a tone digit after the syllable (`péng` → `peng2`).
3. Convert `ü` and `u:` to `v`.
4. Treat spaces and apostrophes as **hard syllable boundaries**.
5. Reject the input if it contains anything other than `a–z`, `1–5`, `0`, spaces, or apostrophes. `0` is treated as tone 5. A digit is only valid directly after letters.

### 5.2 Segmentation

**Every target is exactly two syllables**, so segmentation only needs to split the input into **one or two segments**:

- Remove hard boundaries; if there are more than two segments, there are no results.
- If there is no hard boundary, try every split point (including "no split").
- Each segment, with its optional tone digit, must be one of:
  - **Full syllable**: a valid Mandarin syllable (`peng`).
  - **Prefix**: a valid prefix of at least one syllable (`pen`, `p`, `zh`).
- If there is one segment, it matches the **first** syllable; the second syllable is unconstrained.

A static table of the ~410 valid toneless syllables, plus a prefix set derived from it, makes each check O(1). Since inputs are short, the number of candidate segmentations stays small (at most one per character position).

Example: `xian` produces three candidates:

| Candidate | Segment 1 | Segment 2 |
|---|---|---|
| A | `xian` (full) | — |
| B | `xi` (full) | `an` (full) |
| C | `xia` (full) | `n` (prefix) |

`xi'an` produces only candidate B.

### 5.3 Matching and ranking

For each dictionary entry and each reading, a candidate matches if each segment matches the corresponding syllable's `base` by full equality or prefix, and any typed tone equals that syllable's tone.

Each match gets a **sort key**; the best key across candidates and readings is kept for each entry:

| Priority | Key | Better value |
|---|---|---|
| 1 | Match quality | Both segments full syllables > one prefix > two prefixes > one segment only |
| 2 | Tone agreement | Number of typed tones matched (only tones typed by the player count) |
| 3 | Frequency | Lower `frequencyRank` |
| 4 | Alphabetical | Toneless pinyin, then simplified form |

Results are deduplicated by `WordId`, so script variants never appear twice. Already-submitted entries stay in place but are flagged `disabled`.

**The ranking function is pure:** `rank(input, dictionary) → WordId[]`. It takes no other parameters.

### 5.4 Index format and performance

A two-character dictionary has tens of thousands of entries. A **linear scan of compact typed arrays** is fast enough and much simpler than a trie:

- Entries are pre-sorted by frequency, so a scan can stop early once enough top-quality results are found.
- Entries are **bucketed by the first letter** of each reading's first syllable, so most queries only scan a small fraction of the data.
- Strings (characters, pinyin) are stored in a shared string table; entries hold offsets.
- The file is a custom binary format with a version header, loaded with `fetch` → `ArrayBuffer` in the worker.

**Budgets:**

| Metric | Target |
|---|---|
| Index size (Brotli/gzip) | ≤ 1.5 MB, excluding glosses |
| Glosses (compressed) | ≤ 800 KB, loaded after the index |
| Index load in worker (mid-range Android) | ≤ 500 ms |
| Query latency, keystroke → rendered suggestions | ≤ 100 ms (p95) |
| Worker query time alone | ≤ 20 ms (p95) |

If the scan misses the budget on test devices, switch to a prefix trie keyed by the first segment; the ranking interface does not change.

### 5.5 Worker protocol

```ts
// Main thread → worker
type WorkerRequest =
  | { type: "init"; dictionaryUrl: string; glossesUrl?: string }
  | { type: "query"; requestId: number; input: string; script: Script;
      submitted: WordId[]; limit: number };

// Worker → main thread
type WorkerResponse =
  | { type: "ready" }
  | { type: "results"; requestId: number;
      items: { id: WordId; text: string; pinyin: string; gloss?: string;
               disabled: boolean }[];
      totalMatches: number }
  | { type: "error"; message: string };
```

The UI ignores responses whose `requestId` is older than the latest request. No debounce is needed while queries meet the budget.

### 5.6 Input component behavior

- One `<input>` field with attributes `inputmode="text"`, `autocomplete="off"`, `autocorrect="off"`, `autocapitalize="off"`, and `spellcheck="false"`.
- **Mode detection:** if the value contains CJK characters, the field switches to native mode for that entry; otherwise it uses pinyin mode.
- **IME guard:** track `compositionstart` / `compositionend`. Ignore Enter while composing, when `event.isComposing` is true, or when `keyCode === 229`. Some Android keyboards don't send reliable composition events, so test them on devices (§13.3).
- **Combobox:** follows the WAI-ARIA 1.2 combobox pattern (`role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, `role="listbox"` / `role="option"`). A polite live region announces the result count.
- **Keyboard visibility:** use the `visualViewport` API on the web and Capacitor's Keyboard plugin on Android, so the suggestion list and pending row stay above the on-screen keyboard.

## 6. Game core

### 6.1 Scoring

```ts
type TileState = "correct" | "present" | "absent";

/** Both arguments are canonical WordId characters, in the same script. */
function score(guess: string[], answer: string[]): TileState[] {
  const result: TileState[] = guess.map(() => "absent");
  const remaining = new Map<string, number>();

  // Pass 1: exact matches
  guess.forEach((ch, i) => {
    if (ch === answer[i]) result[i] = "correct";
    else remaining.set(answer[i], (remaining.get(answer[i]) ?? 0) + 1);
  });

  // Pass 2: misplaced matches, consuming remaining occurrences
  guess.forEach((ch, i) => {
    if (result[i] === "correct") return;
    const n = remaining.get(ch) ?? 0;
    if (n > 0) {
      result[i] = "present";
      remaining.set(ch, n - 1);
    }
  });

  return result;
}
```

**Comparison is always done on canonical simplified forms**, after resolving the guess to a `WordId` through the dictionary. Each character position is mapped to its simplified form using the entry's aligned forms. This makes simplified and traditional guesses score the same way. The UI then displays each tile in the selected script.

### 6.2 Game state machine

The game is a reducer: `(state, event) → state`. It's a pure function that is used by both daily and practice modes.

```ts
interface GameState {
  puzzleId: string;
  mode: "daily" | "practice";
  answerId: WordId;
  contentVersion: string;
  guesses: { wordId: WordId; tiles: TileState[] }[];
  hintsUsed: ("topic" | "sentence" | "pronunciation")[];
  status: "active" | "won" | "lost" | "expired";
  startedAt: string;     // ISO timestamp
  completedAt?: string;
}

type GameEvent =
  | { type: "SUBMIT"; wordId: WordId }
  | { type: "USE_HINT"; hint: "sentence" }
  | { type: "EXPIRE" };
```

**Transition rules:**

- `SUBMIT` is ignored unless `status === "active"`. Duplicate `wordId`s are rejected (the UI shows the duplicate message).
- After the 6th non-winning guess, `status` becomes `"lost"`.
- `USE_HINT` accepts only sentence hints after 3 failed guesses. Share `isHintAvailable` between the state update and sentence control. Topic is not an available hint. Legacy pronunciation entries remain assisted but are not rendered.
- `EXPIRE` changes `active` → `expired`.
- `isAssisted(game)` counts sentence or legacy pronunciation usage, ignoring legacy topic entries. Sharing, history, and statistics use this same helper.
- Render the actual topic above the board immediately in daily and practice, without a placeholder, reveal button, or hint-state update. Help describes topic as always visible and not a hint. Lower hint cards render sentence clues only.
- Sentence cards default to Chinese with an accessible Show/Hide translation toggle. Bundle a dedicated `hintEnglish` for every word, preserving blanks from the Chinese clue; do not derive it from `exampleEnglish` or glosses. Translation visibility is local component state, reset by the puzzle ID, and does not consume guesses or add another hint entry.
- Keep the shared help/onboarding modal compact and visual: input steps, labeled correct/present/absent tiles, a pronunciation example reusing `ToneGlyph` and `PinyinFeedback`, and concise hint captions. Do not render a script selector in the modal. Use `--color-brand` (green) for matching pronunciation text/borders and `--color-error` (red) for differences; icons inherit the text color. This mapping is independent of high-contrast character-tile colors. Constrain the dialog to the dynamic viewport height with vertical scrolling so all content and actions remain reachable.

Validation that needs the dictionary (whether the guess is a real word) happens before the event is dispatched. The reducer receives only valid `WordId`s.

### 6.3 Daily puzzle selection

- **Puzzle date** = the calendar date in `Asia/Shanghai`. China uses UTC+8 with no daylight saving, but use `Intl.DateTimeFormat` with `timeZone: "Asia/Shanghai"` anyway so the intent is explicit.
- `content/daily-schedule.csv` (`date,id`, consecutive dates with no gaps) is the committed source of truth. `npm run content:schedule` (`tools/build-schedule.mjs`, options `--days`, default 365, `--today`, `--seed`) extends it to cover today + N days in Asia/Shanghai. It never modifies entries dated today or earlier and fails if one of those references an unapproved word; future entries whose word is no longer approved are replaced. New entries pick never-scheduled approved words first, ordered by `sha256(seed:id)` so the order does not depend on CSV order, then the least recently scheduled word.
- `npm run content:curated` validates the schedule (date format, contiguity, every ID approved) and emits `schedule: { start, answerIds }` in `src/generated/curated.json`; it warns when the schedule is missing or ends within 60 days.
- `dailyAnswerId(date, schedule, pool)` in `src/game.ts` returns `schedule.answerIds[date - start]` when present and approved. Otherwise it falls back to `pool[fnv1a(date) % pool.length]`, which is deterministic for a given content release but not across releases. With server content updates (not implemented), a missing date should instead try the latest manifest and then show the "needs an internet connection" state.
- On start, the `GameState` records `answerId` and `contentVersion`. Later content updates never change an existing game.
- On app start and on `visibilitychange`, compare the current puzzle date with the active game's date and dispatch `EXPIRE` if it has passed. Schedule a timer for the next midnight while the app is open.

**Device clock changes:** the game trusts the device clock. Results are stored by puzzle date, and a past date's result is never overwritten. Moving the clock backward cannot replay a completed puzzle.

### 6.4 Practice selection

- **General practice:** pick a random answer-pool word, excluding today's daily answer, scheduled future answers within the next 30 days, and the last 50 practice words. If the 30-day exclusion leaves no word (small pools), only today's answer is excluded.
- **Saved-word review:** pick randomly from saved words, preferring those not reviewed recently.
- Practice `puzzleId` = `p_<uuid>`.

### 6.5 Streaks and statistics

Computed from stored daily results, not stored as counters, so they cannot drift:

- **Current streak:** count consecutive won puzzle dates backward from today, or from yesterday if today isn't finished yet.
- **Best streak:** longest run of consecutive won dates.
- **Guess distribution:** wins grouped by guess count.

### 7.2 Persistence rules

- Write the game state after every accepted guess, hint, and status change, **before** showing the result animation.

- **Migrations:** use Dexie version upgrades. Never delete user data in a migration without a tested conversion.
- **Reset local data:** delete the database and reload, after confirmation.

## 10. Advertising

### 10.1 Interface

```ts
interface AdService {
  init(): Promise<void>;                        // Includes consent flow
  canShowBanner(): boolean;
  mountBanner(slot: HTMLElement): Promise<void>;
  unmountBanner(): void;
}
```

**Implementations:**

| Implementation | Used on | Notes |
|---|---|---|
| `AdSenseAdService` | Web/PWA | Banner only. |
| `AdMobAdService` | Android | Banner only; no rewarded hints. |
| `NoopAdService` | Tests, development, and when ads are disabled | Always unavailable. |

The implementation is chosen at startup with `Capacitor.isNativePlatform()` and a build-time `VITE_ADS_ENABLED` flag.

### 10.2 Rules

- **Banner slot:** a fixed-height container placed only on the results screen, below the learning card and primary actions. The height is reserved even when no ad loads.
- **Rewarded hints:** disabled; no ad may unlock a full-pinyin clue.
- **Load lazily:** ad SDK scripts are loaded only after the first puzzle screen renders, so they don't affect startup time.
- **Consent:**
  - Android: use Google's User Messaging Platform (UMP) through the AdMob plugin, before requesting ads.
  - Web: use a Google-certified consent management platform where required (e.g. EEA/UK).
  - Without consent, request non-personalized ads only, or none, according to the applicable rules.
- **Test IDs:** development and CI builds always use Google test ad unit IDs. Production IDs come from environment variables.
- **Region note:** Google ad services are not available in mainland China. Players there should get a normal game with no ads and no errors.

## 13. Testing strategy

### 13.1 Unit tests (Vitest)

- **Scoring:** all states, repeated characters (`谢谢` vs `谢意`), and simplified/traditional equivalence.
- **Game machine:** every transition, immediate topic visibility without assistance, sentence hint unlock rules, legacy topic exclusion from assisted accounting, suppression of legacy pronunciation hints, expiry, and duplicate guesses.
- **Daily selection:** midnight boundaries in `Asia/Shanghai` tested with devices in UTC−10, UTC, and UTC+14.
- **Streaks:** gaps, losses, unfinished today, and clock moved backward.
- **Pinyin normalization and segmentation:** toneless, numbered, tone-marked, `v`/`u:`, abbreviations, apostrophes, full-width input, and invalid characters.
- **Search:** 多音 words reachable by every reading; deduplication across scripts; disabled submitted words.
- **Ranking independence:** run the same queries with several different answers loaded in the app and assert identical results. Also, the ESLint import rule from §4.3 is checked in CI.
- **Share text:** spoiler-free output, assisted marker, high-contrast emoji.

### 13.2 End-to-end tests (Playwright)

- Complete a daily puzzle with pinyin, and with simulated IME composition events.
- Enter during composition and Enter without a selection don't submit.
- Reload in the middle of a game restores the exact state.
- Offline: the app works after the first visit; practice works offline.
- Simplified/traditional switch in the middle of a game.
- Ad service returning `"cancelled"` and `"unavailable"` doesn't change state.
- Mobile viewport (360 × 640) with a simulated on-screen keyboard.
- Automated accessibility checks with axe-core.

### 13.3 Manual device testing

Run before each release on at least two real Android devices (one low-end):

| Area | Check |
|---|---|
| Keyboards | Gboard (English, Pinyin, Zhuyin), Samsung Keyboard, Sogou, and SwiftKey |
| Pinyin field | No autocorrect, autocapitalization, or suggestion-bar insertion |
| Native input | Candidate selection with Enter never submits |
| Layout | Suggestions stay visible with each keyboard open |
| Ads | Consent flow and banner success/no-fill (test IDs); no rewarded hint controls |
| Lifecycle | Background past midnight, then resume |

### 13.4 Content tests

`validate-content.ts` runs in CI on every change to `content/` or `tools/`.
